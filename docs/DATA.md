## Three states, not two

A ZIP can be in one of three conditions, and collapsing any pair of them is how a tool starts lying:

1. **Absent from the dataset.** No row at all. `zipcheckup_lookup_zip` returns `zip_not_in_dataset`. Example: `00000`.
2. **Present but entirely empty.** A row exists and every field is blank. **1,335 of 42,679 rows are like this.** The tool returns `row_state.state = "present_but_entirely_empty"`. Example: `99999`.
3. **Present with some values.** Even here, coverage is per-field. Example: `01004` (Amherst, MA) has exactly one known metric out of fourteen.

None of the three is a finding of safety.

## Caveats that matter

**A reported lead level of `0` is not zero lead.** Thousands of ZIPs carry exactly `0` in `lead_level_mg_l`. A laboratory cannot report a true zero; the value means "below the detection limit". Every such value ships with `qualifier: "reported_as_zero_non_detect"`.

**`copper_action_level_exceedance` only ever records `true`.** 3.1% of rows carry a value and that value is always `true`. A blank therefore distinguishes neither "no exceedance" nor "never tested", so it is returned as `unknown`, never as `false`. Rendering it as `false` would tell 96.9% of the country that its copper was tested and passed.

**`boil_water_advisories` is empty for every row.** It is nevertheless shipped, as a permanent documented unknown. Telling an agent "this field exists in the schema and holds nothing" is safer than omitting it and letting the agent conclude that no advisories were issued.

**A ZIP is not a water system.** The dataset maps each ZIP to one public water system, but ZIP boundaries and service-area boundaries are different things and do not nest. A real example, surfaced by an agent using these tools: the dataset assigns `90210` to the Los Angeles Department of Water and Power, while the City of Beverly Hills operates its own water system for much of that area. Treat `pwsid`/`system_name` as "the system the dataset associated with this ZIP", and verify the provider for a specific address before acting.

**`home_safety_score` is a vendor composite, not a measurement.** Its inputs and weights are not documented in the open dataset, and no regulation defines a passing value, so it ships with `threshold.status = "not_applicable"`. It is present for only 26.1% of ZIPs; a missing score is not a low score.

**Violation counts are counts of records, not of events.** A zero means no record was matched, which can equally mean nothing happened, nothing was reported, or nothing was matched to this ZIP.

## Withheld columns

`ccr_contaminant_count` and `ccr_violation_count` are in the source schema but empty for all 42,679 rows, and unlike `boil_water_advisories` they add nothing an agent can act on, so they are excluded from the shipped shards. `BUILD.json.withheld_columns` records the exclusion.

A separate companion file in the upstream bucket, `ccr_copper_90th_ppb`, was previously reported to carry ppm values labelled as ppb - a 1000x understatement against the 1,300 ppb action level. This project does not read that file. Nothing here should be extended to a column whose fill rate and units have not been checked first.

## Build rules

`scripts/build-data.mjs` refuses to produce artifacts unless every assertion holds:

- every row has exactly 25 fields;
- non-empty `zip` matches `^[0-9]{5}$`;
- non-empty `state` matches `^[A-Z]{2}$`;
- non-empty `home_safety_grade` matches `^[A-F]$`;
- non-empty `radon_zone` matches `^[123]$`;
- non-empty `has_active_issues` is `true` or `false`.

These exist because **2,158 rows contain quoted fields with embedded commas**. Parsing with `split(',')` shifts every later column and yields values like `home_safety_grade: 59` - health data that is wrong but looks plausible. The parser is RFC4180 (`scripts/lib/csv.mjs`) and the assertions are what catch a regression back to the naive path.

Empty cells are dropped at build time rather than written as `0`, `false` or `""`, so absence stays distinguishable from a measured value all the way to the agent.
